## 2026-11-03 (evening) — CAUSE PROVEN: the Metal glitch is stale textures
- **Proof (session 722, 18:51, `reports/report-2026-11-03-185116` and `logs/live-after-report-2026-11-03-185116.png`):** Bruce loaded in to black buildings. Report saved at 18:51:16 (black), `reload_stale` at 18:51:21 reloaded **804** textures whose guest memory no longer matched their upload, and the frame after, same spot and view, is fully and correctly textured; the live screen stayed right.
- **What it means:** the game rewrites texture memory (streaming a district's textures on load or teleport) through some path that doesn't trip the page watch, so `g_page_versions` never moves, `FindTexture` never re-hashes, and Metal keeps drawing the old data: black, magenta or flat colours depending on what was there. It clears by itself only when something else happens to bump those pages.
- **Next, the fix (two parts):** (1) a safety net in `TextureCache`: re-hash texture contents round-robin, a share of the cache each frame, and reload on a mismatch, so a missed write heals within about a second whatever caused it; (2) find the write path that skips the watch (suspects: host-side kernel writes into guest memory such as decompression or file reads that don't trigger callbacks, or a watch disarmed and not re-armed) and fix it at the source.
- `reload_stale` stays as a debug word. The 18:49 title-screen check found 16 stale there too, so this happens all the time and only shows when big building textures are hit.

## 2026-11-02 — Fences and ring space wait for Metal (SDK patch 0017): the one-frame flicker

## 2026-11-02 — The swap presents Metal's picture directly (SDK patch 0016)

## 2026-11-02 — Exposure readback from Metal
- **What the game reads:** one lock site, `825AA170`, once a frame, rotating through three 320x180 8888 textures at `F9578`, `F95B6` and `F95F4`. Each is read about two frames after it's resolved. Nothing else showed up in a 300-frame street run. A read that doesn't lock wouldn't show.
- **What it does with them:** auto-exposure. A 256-bin histogram of byte 0 of every pixel, leaving out the brightest 600 samples or so. Byte 0 is the target's alpha, so the other three bytes don't matter to the game.
- **What's in:** `ReadResolve` copies a resolve to a shared buffer in the frame, for any texture the game has locked, matched on page and size. Every 30th lock compares it with what the game is about to read. `crackdown_native_exposure` (default off) overwrites guest memory at the lock, so the game really reads Metal's picture.
- **Layout, for the takeover:** guest pixels are tiled, and each is Metal's four bytes reversed. Addresses from `0xE0000000` up sit `0x1000` further along, which cost one wrong run: the picture came out shifted one 32x32 tile.

| Spot | Emulator input | Metal input | Reads served by Metal |
|---|---|---|---|
| Shift+3 street | 75.01 | 75.06 | 301, none late |
| Tunnel | 76.16 | 73.15 | 300, none late |
| Ocean high | 110.02 | 117.42 | 300, none late |

## 2026-11-02 — Occlusion queries counted in Metal, side by side with the emulator
- **What's in:** Metal gives every occlusion query its own visibility slot, in counting mode, in the pass. `826C0B38` (issue) marks where queries begin and end in the stream, after reading the ring up to that point so a query's own draws land inside it. `826C0D38` (get data) is hooked for the emulator's answer. - **The emulator doesn't count samples.** Its largest answer is 8, where Metal counts hundreds. The SDK begins queries with no precise flag, and from memory MoltenVK's non-precise mode only reports visible or not, though I haven't read its source. So only visible or hidden can be compared, and the `samples_ratio` of about 400 means nothing.
- **Why that matters, the game does use counts.** Four places read answers:

  - `825D1F68` stores a count, and `825D1FA0` tests count > 1000. The emulator's largest was 2, so that test never passed here. Not known what it drives.
  - `823A3EC8`, per-object queries around real draws, stored at +1796 on the object.
- **Corona loop:** every quad draws every frame, and a query wraps it only once the last answer is in. So a frame has about 200 quads and far fewer queries, and each answer takes about four frames in the emulator.
- **Metal only disagreements:** 398 of 622 were 64 samples or more, and they're street lamps. `mark_queries` paints them: quads floating in open air around lamp heads, with only the lamp itself notched out of them. Nothing stands in front, so Metal's answer looks right. Not known why the emulator says 0.

- **Emulator only (236):** not looked at. The ones sampled were object queries answering 1, where Metal said 0.
- **For the takeover:** write the result into the end block at the query's `+24` pointers, one per tile: ZPass at `+16`, Total at `+0`, little-endian, zeroing the begin block at `+32`. Total needs a second count for coronas, such as the same quad with depth off. The game's fence check at `+20` has to pass as well.

## 2026-10-30 (evening) — Real fix: shaders were 10-20x slow from SPIRV-Cross `optnone` helpers
- **Cause:** Xenia's SPIR-V marks most float math `NoContraction`. SPIRV-Cross (inside MoltenVK) emits those operations as calls to `spvFAdd`/`spvFMul`/`spvFSub` helpers declared `[[clang::optnone]]`. Metal cannot optimize or inline them, so shaders reached 146-254 registers with spills and starved Apple GPU occupancy. A standalone harness (`work/experiments/menu-bench/harness/`) times dumped MSL with dummy resources. Stripping `optnone` takes the top menu shaders from 1.0-2.9 ms per full-screen draw to 0.09-0.31 ms.
- **Changed:** SDK patch `0009-contract-shader-math.patch`. `vulkan_contract_pixel_shader_math` and `vulkan_contract_vertex_shader_math` (defaults false in the SDK) skip `NoContraction`. The vertex variant decorates the position `Invariant` to avoid multipass z-fighting. The patch also includes experiments that showed no gain: `vulkan_plain_multiply` (skip Xenos 0*x emulation) and `vulkan_assume_unsigned_textures`. **Both contraction switches are enabled in the app bundle's `crackdown.toml`** (local prototype defaults; the repo's `config/crackdown.toml` is unchanged).
