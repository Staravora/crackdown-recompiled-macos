## 2026-10-30 (night) — Shader cache now persists; compile hitches gone after the first visit
- **Cause:** The pipeline and shader storage files are opened with `"a+b"`. macOS (BSD libc) starts reading at the end of the file, so every launch failed to read the header, judged the file invalid and truncated it. Startup precompilation never ran, and every pipeline compiled live as it appeared.
- **Changed:** `0010-persistent-pipeline-storage.patch` seeks both storage files to the start after opening. It also logs "Storage has N pipeline descriptions…" at startup. The D3D12 cache uses the same pattern, but Windows starts reading at the beginning of the file. Upstream-worthy as a Mac fix.
- **Measured:** Warm-up session: 654 live pipeline compiles; median 13.7 FPS, 10th percentile 10.1, 90th percentile 21.5. Next launch: 356 pipelines precompiled at startup, then 2 live compiles; median 14.3, 10th percentile 11.5, 90th percentile 26.4. Bruce: "hitches gone". New areas still compile once on first visit; the cache grows as he plays (`user_data/cache/shaders/shareable/4D5307DC.fbo.vk.xpso`).
- **Next:** Steady state is still ~14 FPS in gameplay. Profile a gameplay frame (capture without `MVK_CONFIG_SHADER_DUMP_DIR`), rank gameplay shaders with the harness, and look at the remaining vertex/geometry and pass costs.

## 2026-10-30 (evening) — Real fix: shaders were 10-20x slow from SPIRV-Cross `optnone` helpers
- **Cause:** Xenia's SPIR-V marks most float math `NoContraction`. SPIRV-Cross (inside MoltenVK) emits those operations as calls to `spvFAdd`/`spvFMul`/`spvFSub` helpers declared `[[clang::optnone]]`. Metal cannot optimize or inline them, so shaders reached 146-254 registers with spills and starved Apple GPU occupancy. A standalone harness (`work/experiments/menu-bench/harness/`) times dumped MSL with dummy resources. Stripping `optnone` takes the top menu shaders from 1.0-2.9 ms per full-screen draw to 0.09-0.31 ms.
- **Changed:** SDK patch `0009-contract-shader-math.patch`. `vulkan_contract_pixel_shader_math` and `vulkan_contract_vertex_shader_math` (defaults false in the SDK) skip `NoContraction`. The vertex variant decorates the position `Invariant` to avoid multipass z-fighting. The patch also includes experiments that showed no gain: `vulkan_plain_multiply` (skip Xenos 0*x emulation) and `vulkan_assume_unsigned_textures`. **Both contraction switches are enabled in the app bundle's `crackdown.toml`** (local prototype defaults; the repo's `config/crackdown.toml` is unchanged).
- **Measured:** Menu goes from 19-23 to ~61-63 FPS uncapped. Gameplay goes from ~5 to 10-13 FPS in the garage, ~8-10 FPS in the city, peaks of 22. Bruce saw correct rendering, including the city and no z-fighting. Remaining sub-8 FPS dips line up with first-use pipeline compilation.
- **Bugs seen:** The game froze with audio running after the window went fullscreen during a capture-enabled run. That run combined `MVK_CONFIG_SHADER_DUMP_DIR` with the capture variables, and MoltenVK then wrote the trace to an invalid path (the dump directory), so the freeze may be specific to that setup. Do not combine those variables. Pre-existing black/flashing title on about half of launches; relaunch.
- **Next:** Profile a gameplay frame with the fix (capture without shader dump) and rank shaders with the harness on gameplay MSL dumps. Reduce compile hitches (pipeline precompilation/storage, `vulkan_async_skip_incomplete_frames`). Consider landing contraction as a Mac default in source and repo config.

## 2026-10-30 (late afternoon) — Root cause: translated pixel shaders need 146-254 registers
- **Measured (Xcode GPU profile of the menu frame, `work/experiments/menu-bench/menu.gputrace`, 68.9 ms GPU):** The top fragment shaders by cost are 36.9% (146 registers, 32 B spilled), 25.6% (204 registers, 32 B), 12.1% (254 registers, 80 B), 2.3% (188) and 2.3% (110). One game vertex shader uses 226. Internal compute shaders use 22-96 with no spills. With this many registers per thread, Apple GPUs keep very few threads resident and cannot hide texture latency. That explains every earlier symptom: GPU busy at ~15% ALU, ~12% occupancy, cost scaling with pixels, and simple post-process shaders taking milliseconds.
- **Ruled out:** `MVK_CONFIG_FAST_MATH_ENABLED=0` is slower (19.1 FPS), so fast math is already on by default. The "1"/"2" runs are invalid because the game entered gameplay mid-run.
- **Xcode replay:** It works now. It was waiting on something Bruce cleared in Xcode. Open the trace, click Profile, then Show Performance → Shaders tab for registers and spills.
- **Next:** Cut register pressure in the SPIR-V translator, verifying each change with a fresh capture's register counts and the menu benchmark. Candidates: runtime per-component sign/gamma switches after every fetch (specialize signs into the shader modification key); sampling both unsigned and signed views; Xenos `0*x` multiply emulation (`min(abs)==0` selects) on every mul; NoContraction/`fma(l,r,0)` wrappers; the emulated register file and loop-carried `xe_var_*` state.

## 2026-10-30 (afternoon) — Outline shader's texture reads are the menu bottleneck
- **Method:** Unattended menu benchmark (`work/experiments/menu-bench/bench.sh <label> [ENV=..] -- [args]`): launch with no frame cap, wait 55 s, take the median of the last 8 FPS samples. Nobody may touch the game. Launcher player settings (`internal_render_scale`, `anisotropic_override`, `crackdown_msaa_compatibility`) are ignored on the command line; set them in `user_data/settings.toml` and restore it after.
- **Measured (menu ~20-23 FPS baseline, GPU ~88% busy):** At 50% render scale the menu runs at 44.9 FPS, so it is pixel-bound. Skipping the outline/edge post-process (PS `B20B230BE9FD2568`, 2 full-screen quads per frame, 8192x8192 screen-space viewport, 2x MSAA) gives ~30.6 FPS, even when its textures still load. Zeroing its texture fetches gives 28.0 FPS. Zeroing only tf1 (k_8_8_8_8 1280x484, bilinear, mutable unsigned/signed format) gives 26.4 FPS. Zeroing only tf0 (k_24_8_FLOAT 1280x720 → R32_SFLOAT, point) gives no change. Five filtered RGBA8 reads per pixel cost ~5 ms, 20-40x below the expected M1 texture rate.
- **Ruled out (no change):** MoltenVK `ALLOW_METAL_FENCES=0`, `USE_MTLHEAP=1`, `ALLOW_METAL_EVENTS=0`, `USE_METAL_ARGUMENT_BUFFERS=0`; pixel-rate A2C; `anisotropic_override=0`; implicit-LOD sampling (`vulkan_implicit_lod_2d_fetches`); unbranched samples (`vulkan_unconditional_texture_samples`); scissor clamp (`vulkan_clamp_scissor_to_framebuffer`). Separate signed images (`vulkan_separate_signed_textures`) are worse, at 20.7 FPS.
- **Changed:** Patch `0008-shader-cost-experiments.patch` adds all flags above plus `vulkan_skip_pixel_shader=[draw:]HASH`, `vulkan_zero_texture_fetches_in_shader=HASH[:N]` and `vulkan_log_pixel_shader_draws=HASH`. All default off; staged and verified.
- **GPU capture:** MoltenVK on-demand capture works (`METAL_CAPTURE_ENABLED=1 MVK_CONFIG_AUTO_GPU_CAPTURE_SCOPE=3 MVK_CONFIG_AUTO_GPU_CAPTURE_OUTPUT_FILE=…`, then write `1` once to `/tmp/MoltenVKCapturePipe-*`; a second write errors harmlessly). An 821 MB menu frame is saved in `work/experiments/menu-bench/menu.gputrace`. Xcode replay hung at "connecting to My Mac", possibly waiting on a hidden permission prompt.
- **Next:** Replay the capture with the shader profiler and inspect the tf1 texture (storage mode, pixel format, compression, usage) and the outline draw's per-line cost. Candidates still open: texture storage or layout chosen by MoltenVK for mutable-format or transfer-destination images, and sampler state.

## 2026-10-30 (later) — Upload hoist works; pass count is not the main cost
- **Changed:** SDK patch `0006-hoist-shared-memory-uploads.patch` (`vulkan_hoist_shared_memory_uploads`, default false). Index, vertex and memexport uploads requested during draw setup are replayed at a hoist point before the open render pass, between two global barriers, unless a draw already in that pass accessed the range. Texture-load uploads are excluded because their compute dispatch relies on the upload ending the pass. In the garage, ~135 uploads/frame are hoisted, breaks drop from ~330 to ~237/frame, and the image is correct. FPS goes from ~5 to ~5.5 only.
- **Changed:** `0007-pass-timing-diagnostics.patch` (`vulkan_log_pass_timings`, default false). It adds GPU timestamps around every render pass in one submission every 3 s, logs the slowest passes with draw count, pipeline and the work that follows, and logs pipeline and transfer-pipeline handles with their shader hashes. All patches are staged and verified with `check-macos-sdk.py`.
- **Measured:** A handful of passes on the 1280x1024 main target take 6-26 ms each. But the *same* menu pass (same pipeline, 26 draws) measured 20.9 ms and 6.3 ms in different samples, so the time is largely stalls on dependencies, not shader cost. That matches counters showing the GPU busy at low utilization. Menu-heavy shader `B20B230BE9FD2568` is the outline/edge post-process: 10 fetches, ~1000 lines of MSL, explicit-gradient array sampling with runtime signedness switches. It is bulky but not the cause on its own.
- **Ruled out (menu benchmark, unattended):** `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS=0` makes no change (~18 FPS). The MTLHeap result is invalid because Bruce entered gameplay mid-run.
- **Pre-existing bug:** About half of launches sit at the title with a black, white or flashing image (game at ~20 FPS, stuck at 39-43 pipelines, input ignored). It reproduces with the original pre-session library and with skip-intro off. Relaunch to get past it. A launch via `open -a` gave the window focus correctly. Separately, moving the window to another Aerospace workspace blanks it.
- **Next:** Find what the stalled passes wait on. Take an Xcode GPU capture of one gameplay frame (MoltenVK `MVK_CONFIG_AUTO_GPU_CAPTURE_SCOPE` with `METAL_CAPTURE_ENABLED=1`) and inspect encoder dependencies, or time the barriers and compute work between passes. Menu benchmarking: `bench.sh`-style unattended launches with `--crackdown_frame_rate=0`, last 8 samples (~18 FPS baseline), only while nobody touches the game.

## 2026-10-30 — Pass-break cause measured; two hypotheses ruled out
- **Measured:** Agency garage ~5 FPS. GPU counters (xctrace "Metal GPU Counters") show the GPU ~82% busy with Crackdown work yet ALU ~15%, bandwidth ~5%, fragment occupancy ~12%, vertex occupancy ~1%: fixed per-render-pass overhead, not shader or bandwidth load. New diagnostic counts **~330 pass breaks/frame**: ~128 shared-memory upload barriers (`VulkanSharedMemory::UploadRanges`), ~120 occlusion-query begin/end, ~34 EDRAM transfers (`DumpRenderTargets`), ~21 framebuffer switches, ~27 other barriers. Evidence: workspace `work/performance-pass-breaks.json`.
- **Ruled out:** Per-sample shading. SPIRV-Cross forced `[[sample_id]]` on every A2C-capable pixel shader; patch 0004 (`vulkan_pixel_rate_alpha_to_coverage`, default false) fixes it with a correct image but no FPS change. Occlusion queries alone: `occlusion_query_enable=false` gives only ~6.3 FPS and shows markers through walls (diagnostic only). Compositor: fullscreen is ~4.2 FPS. GPU clock: not throttled.
- **Changed:** SDK patches `0004-pixel-rate-alpha-to-coverage.patch` and `0005-pass-break-diagnostics.patch` (`vulkan_log_pass_breaks`, default false). Both are staged in the installed SDK and the app, verified by `check-macos-sdk.py`. Pre-change libraries: workspace `work/experiments/pixel-rate-a2c/previous`.
- **Next (pending Bruce's choice):** Hoist shared-memory upload copies ahead of the current pass when no draw in that pass has read the range (splice point in `DeferredCommandBuffer`), and keep query begin/end inside passes with batched resets and copies.
