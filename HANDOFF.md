## 2026-10-31 (afternoon) — Flat colour fixed: MoltenVK left the drawable at 1x1 (`0014`)
- **Cause:** `MVKSwapchain::initCAMetalLayer` sets `drawableSize` to the new extent, then compares that extent with the size it just set, so the check always passes. With an `oldSwapchain` that still has a presentation in flight, `forceUnpresentedImageCompletion` then sets `drawableSize` to `{1,1}`. The new swapchain draws to one pixel, and the window stretches it. That is why the colour was the guest output's top-left pixel, and why the rate depended on timing: 1 in 6 at startup, nearly always when leaving fullscreen with frames in flight.
- **Fix:** on macOS the presenter destroys the old swapchain first and creates the new one with no `oldSwapchain`. `destroy()` does the forcing while the real size is still to come. No MoltenVK rebuild needed.
- **Hover menu:** `0014` also sets `NSZoomButtonShowMenu` false before SDL starts AppKit. It has to be that early: set just before window creation, the menu still opened on a fresh preference. The green button still switches fullscreen on click.
- **Verified:** with the swapchain change, 5 of 5 fullscreen exits showed the real picture, including a full on-off cycle, against 8 of 8 flat before. The hover menu no longer held the main thread once the preference moved (1 run). 6 of 6 windowed launches reached gameplay with a picture. That alone is weak for a 1 in 6 bug (a third of the time 6 clean runs would happen anyway); the stronger argument is that the code path can't run without an `oldSwapchain`.
- **No cost:** interleaved, old against new, median of three: 26.09 and 25.66 FPS, p99 87 and 87 ms, frames of 80 ms or more 8 and 9. The small gaps sit inside run-to-run noise.
- **Open:** the 52 ms p99 baseline did not come back with either build (79-99 ms today), so that baseline run was not typical, or something else changed. Bruce's normal launcher path and the green button click are not tested; the tests used `--crackdown_skip_launcher` and the Window menu. The diagnostic patch stays in `work/experiments/flat-colour`.

## 2026-10-31 (late night) — Guest memory leaked on every launch; swap reached 40 GB
- **Symptom:** macOS "out of application memory" during play. Swap was 40.3 of 40.96 GB, with the game closed, while all running processes added up to about 16 GB, so 24+ GB belonged to no process. Free disk fell to 15 GB, since swap lives on disk.
- **Cause:** `Memory::Initialize` creates a POSIX shared memory object with a new name each launch (`xenia_memory_<tick>`). Only `Memory::~Memory` unlinks it, and every exit path is `std::_Exit`, so a normal close, a kill and a crash all leave it behind with whatever guest memory was touched. Benchmarks launch and kill the game constantly, which made it much worse. The code path is confirmed. That it accounts for all the unowned swap is a strong inference, not yet measured.
- **Fix:** patch `0013` unlinks the object right after creating it. The handle and views keep it alive, and the kernel reclaims it on any exit. A small test confirmed views still alias after the unlink. Staged and verified, verified after a reboot: over three normal exits and a `kill -9`, wired memory stayed at 1.6 GB, anonymous at about 4.9 GB and swap at 0, while the game itself used about 0.8 GB more when running.
- **Reboot result:** swap 40 GB to 0, free disk 15 GB to 67 GB, wired memory 9.6 GB to 2 GB. A reboot clears any leak, so the repeated launches above are the real proof.
- **Play session (8 min):** FPS fell from about 28 to 16, which Bruce saw as throttling. 12 seconds dropped under 12 FPS, with gaps of up to 2 s while crossing the city. Only 2 of 12 had a pipeline created nearby, so shader compiles are not the main cause. Paging under full swap is a candidate, unproven; re-test after the reboot before chasing streaming.

## 2026-10-30 (late night) — Occlusion queries recorded inside render passes: +58%

A guest query becomes one host query per guest render target cache pass it spans (a segment, begun when the pass starts or the query begins inside it, ended when either ends), recorded inside the pass instead of ending it. ## 2026-10-30 (evening) — Real fix: shaders were 10-20x slow from SPIRV-Cross `optnone` helpers
- **Cause:** Xenia's SPIR-V marks most float math `NoContraction`. SPIRV-Cross (inside MoltenVK) emits those operations as calls to `spvFAdd`/`spvFMul`/`spvFSub` helpers declared `[[clang::optnone]]`. Metal cannot optimize or inline them, so shaders reached 146-254 registers with spills and starved Apple GPU occupancy. A standalone harness (`work/experiments/menu-bench/harness/`) times dumped MSL with dummy resources. Stripping `optnone` takes the top menu shaders from 1.0-2.9 ms per full-screen draw to 0.09-0.31 ms.
- **Changed:** SDK patch `0009-contract-shader-math.patch`. `vulkan_contract_pixel_shader_math` and `vulkan_contract_vertex_shader_math` (defaults false in the SDK) skip `NoContraction`. The vertex variant decorates the position `Invariant` to avoid multipass z-fighting. The patch also includes experiments that showed no gain: `vulkan_plain_multiply` (skip Xenos 0*x emulation) and `vulkan_assume_unsigned_textures`. **Both contraction switches are enabled in the app bundle's `crackdown.toml`** (local prototype defaults; the repo's `config/crackdown.toml` is unchanged).
- **Measured:** Menu goes from 19-23 to ~61-63 FPS uncapped. Gameplay goes from ~5 to 10-13 FPS in the garage, ~8-10 FPS in the city, peaks of 22. Bruce saw correct rendering, including the city and no z-fighting. Remaining sub-8 FPS dips line up with first-use pipeline compilation.
- **Bugs seen:** The game froze with audio running after the window went fullscreen during a capture-enabled run. That run combined `MVK_CONFIG_SHADER_DUMP_DIR` with the capture variables, and MoltenVK then wrote the trace to an invalid path (the dump directory), so the freeze may be specific to that setup. Do not combine those variables. Pre-existing black/flashing title on about half of launches; relaunch.

## 2026-10-30 (late afternoon) — Root cause: translated pixel shaders need 146-254 registers
- **Measured (Xcode GPU profile of the menu frame, `work/experiments/menu-bench/menu.gputrace`, 68.9 ms GPU):** The top fragment shaders by cost are 36.9% (146 registers, 32 B spilled), 25.6% (204 registers, 32 B), 12.1% (254 registers, 80 B), 2.3% (188) and 2.3% (110).
